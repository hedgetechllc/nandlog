Testing

A host simulator for everything above the wire, and three device applications for everything at it.

Host simulator

cd sim && make

Builds and runs three configurations — record framing off, framing on, and framing on with internal page copy disabled — under AddressSanitizer and UndefinedBehaviorSanitizer. The whole suite takes milliseconds.

The porting seam is at the SPI command level, so sim/nandlog_port_sim.c emulates a NAND part rather than stubbing out a log: the real chip driver runs on it unmodified, and addressing, status-register handshakes, busy-waiting, the cache register and bad-block bookkeeping are all shipping code under test. The emulated part is built from whatever geometry the compiled driver reports, so the two cannot disagree.

NAND semantics are honoured rather than approximated: erase sets bits, programming may only clear them, a program cut short leaves exactly the prefix that made it, and a page read fills the chip's one cache register.

It can also dump a byte-for-byte image of the emulated part, so the reference parser can be run against something a device would actually have produced.

What it covers

Round trip; a record sized to fill a page exactly; epoch details; write-head recovery across a reboot; factory bad-block markers in the spare area; block retirement; relocation without bus traffic; listing and reading an earlier epoch; a torn page; a rotted payload; a disabled log; reads refused outside a session; the busy timeout ending in nandlog_port_fatal(); and a date-limited read across a backward time step.

On-device tests

Three applications in tests/, for the questions a simulator cannot answer: what the real part does with a command the simulator only pretends to implement, what its on-die ECC does to bytes the log wants to read or write, and how long any of it takes.

TestGatesWrites to the part
test_nandlog_partial_read.cColumn-addressed and short page readsOne scratch page
test_nandlog_page_copy.cnandlog_chip_copy_page()Three scratch blocks
test_nandlog_ecc_marker.cWhether a bad-block marker can be written into the spare area at allFour scratch blocks

All three work only in the top blocks of the reserve, which the log never places a page in, and skip any block already retired. None touches the log region, the metadata ring, or the chip driver's bad-block marker page. They are still write tests: run them on a development board.

Run the read test before deploying a new chip driver. A wrong column byte order does not fail loudly — it reads 0xFF from the wrong place, the factory bad-block scan concludes every block is good, and nothing is retired. The simulator cannot catch it, because it decodes the column address the same way the driver encodes it.

Each test prints its own pass/fail verdict and a timing table. tests/README.md has the build instructions and what each result means.

The reference parser

./tools/nandlog_parse.py image  dump.bin --page-size 4096 --spare-size 256
./tools/nandlog_parse.py stream offload.bin --json

An independent implementation of the on-flash and wire formats, written separately from the library that produces them. The device computes CRC-32 with the IEEE 802.3 polynomial precisely so the parser can verify it with zlib.crc32 and nothing bespoke.

Use it to check a device's output end to end: if the parser and the device ever disagree, one of them is wrong.

What host tests cannot tell you

Nothing about the real part's timing, its ECC, or the board. Those need the device tests above, plus a deployment.
