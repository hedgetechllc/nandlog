nandlog

Append-only, CRC-validated logging on raw SPI NAND, built to keep every committed record across a power cut. No flash translation layer, no filesystem, no heap.

nandlog is a C99 library for devices that collect data for weeks and hand it over in one go — a battery-powered sensor, a tag, a logger. It assumes writes are small and frequent, reads are rare and bulk, and power can be lost at any instant without warning.

What survives a power cut

A record is durable once the call that committed its page has returned: the nandlog_store_record() whose record did not fit and pushed the previous page out, a nandlog_flush(true), or a nandlog_begin_epoch() that committed what was buffered. Records still in the RAM page are lost at a cut, as they would be at any reset; flush on a timer to bound that.

After a cut at any instant, every durable record is delivered intact from the epoch it was logged in, a page the cut tore is reported as a gap, no committed page that still reads is erased, and nothing is programmed a second time — on every boot after the cut, however a torn page that fails its checks reads on each, and however it later drifts, with the exceptions listed below. And a sequence number is an identity: what a read has served under an epoch and sequence number is what that number holds from then on, or a gap if the part loses the page, never other records — a read commits whatever is buffered before it opens, so it never serves a page from RAM.

The simulator's crash-point campaign checks exactly that at every program and erase of fourteen traces, under four models of what a cut does to the operation it lands in, again with a second cut during the reboot and in the logging after it, and then lets every weakly programmed page drift; its fuzzer checks it at random; and a bounded-exhaustive check boots the shipping code over every combination of page states below the write head of a toy part, and cuts every metadata write path at each of its operations (see Testing). This build has not yet run on a real part; the on-device power-cut soak in tests/ is how that changes, and its results are still to come.

The limits of that statement:

  • A page that reads erased in every bit cannot be told from an erased page by any read, so a boot that finds one at the write head programs it again: one a cut stopped before it changed a bit; one the part refused without changing a bit, if the cut also beat the metadata write that records the refusal or every copy of that record is later lost; and a torn page that drifts back to erased before the first boot after its cut has finished listing it. These are the residual second programs. In the log region each lands on the page at the write head, which no read has served, and building with NANDLOG_PASS_OVER_HEAD_AT_BOOT rules them out there, at a price paid at every boot (see Getting started); a metadata or table copy a cut stopped before it changed a bit is still written again, read back and verified, by the next write to its pair.
  • A torn page is listed in the epoch's metadata slot by the first boot that finds it below the write head, before anything is committed after it, and counts as written from then on whatever it reads. A torn page that reads whole — header, payload and ECC all checking — cannot be told from a committed one and is taken as one, so a read may serve it though its commit never returned; that it then never drifts is an assumption of the model, as is that a committed page never comes to read erased in every bit.
  • A slot lists up to 880 runs of passed-over positions on a 4 KB page, 368 on a 2 KB one. An epoch whose list is nearly full is sealed: its slot says so, and every later boot refuses records with NANDLOG_ERR_SEALED and calls nandlog_port_unwritable(), until a new epoch is begun. Reads go on.
  • One unreadable page of the metadata ring or the bad-block table changes nothing; each is written twice, and a copy is read once and judged by every checksum it carries. Both copies share a block, so a copy of the newest record read only at the limit of the part's ECC has the boot write that record again, unchanged, in a fresh block (below). If no copy of the newest slot the epoch acted on holds its list whole, the epoch is sealed; if only its details are lost, it goes on without them. If both copies of a slot are lost outright, the boot goes by the slot before it: an epoch begun since is recovered from its own pages, without its details; positions only the lost slot listed are guarded only by the head search's look past the head it finds; and a failed program it recorded may be programmed again if it reads blank.
  • The bad-block table has to lay the epoch out as it was written. The ring records how many blocks are retired and which of the epoch's own blocks are, and a table that differs — both copies of its newest version lost, or one the recovery utility rebuilt from other marks — seals the epoch. The epoch begun after it starts past the last block that still holds one of the sealed epoch's pages, as the table now lays them out, so none of them is erased as its window. On the Alliance part every retired block also carries a spare-area mark, which counts only when it reads exactly 00h: every boot programs again any that does not; the recovery utility never erases a block that may carry a mark, and reads marks with ECC off.
  • On the Alliance part the table lives in the reserve. If the reserve cannot hold it, a boot gives the driver an aligned pair of blocks from the top of the log region — outside the current epoch, holding nothing a read could serve — which are retired and hold the table from then on; later boots find it by one header read a block down to 48 blocks below the reserve. With no such pair, the marks become the record (degraded mode): a retirement is committed by its block's own mark, read back exactly 00h, and every boot rebuilds the table from every block's mark, about 1.8 s on an 8 Gbit part. A retirement neither can record — a block that refuses even its mark — gets the table a pair in the middle of the call, under the same rules; only with no pair anywhere does the log stop.
  • On the Winbond part a retirement is an entry in the part's own 20-entry remap table, which its factory-bad blocks share. Once it is full a failing block cannot be retired and the log stops taking pages; and that an entry is written whole or not at all across a cut is the part's to guarantee, assumed here and not verified.
  • Corruption that both the part's ECC and CRC-32 miss is outside the model.
  • nandlog_port_fatal() must not return, and a retirement's atomicity rests on the part completing a page program or reporting its failure.
  • An earlier epoch is kept only until the write head sweeps over it, and a block of it the window cannot erase is retired, and so no longer read, a little before that.

Nothing rewrites a page in place. A page of the log read back corrected only at the limit of the ECC is counted (reads_at_ecc_limit) and left to the part's ECC. The metadata is read far harder: every boot reads about ten pages of the newest ring block and of the newest table block, some five million page reads a year at one boot a minute, and both copies of each record sit in that one block, so wear on the block is wear on both. A boot that reads either copy of the newest ring slot, or of the newest table version, only at the limit of the ECC therefore writes it again, unchanged, into a fresh block, whose erase and program start its pages afresh; and nothing that reads back at the limit counts as written, so a page stuck there costs one boot one write, not every boot. That relies on the part reporting the limit before a page goes past it. The Alliance part reports it when a codeword (512 + 32 B) needed all 8 of its corrections, one bit short of loss: enough for errors that build up between one boot and the next, such as read disturb, but not for those of a long period unpowered, which are left to the part's retention rating. The Winbond part has no such verdict, so on it, and on any part, check the read-disturb rating against the boot rate. The head search's first four probes move from boot to boot — with the ring's slot numbering, which a clean boot does not change, and with NANDLOG_BOOT_SALT, which a device that boots often should define (a boot counter that survives a reset, or a random number) — so they do not fall on the same pages every time.

What it does not do

  • Interpret records. A record's contents and length are the application's business; the log stores opaque bytes.
  • Read a clock. Timestamps are supplied by the caller, compared, and never interpreted.
  • Allocate. Everything is static and sized at compile time.
  • Wear-level. The write head sweeps forward and wraps. Anything more would need a mapping table.
  • Random-access update. A page is written once and never revised.

A minimal example

#include "nandlog.h"

if (!nandlog_init())
   return;                        /* no part fitted, or the port would not open */

nandlog_begin_session();
nandlog_begin_epoch(&details, sizeof(details));
nandlog_end_session();

if (nandlog_store_record(RECORD_SAMPLE, milliseconds, &sample, sizeof(sample)) != NANDLOG_OK)
   ;                              /* not stored, and the status says why */
nandlog_flush(true);

See Getting Started for the complete picture, including reading data back.

Requirements

  • A C99 compiler. Build with -fno-strict-aliasing.
  • A little-endian target: the on-flash structures are native integers. A compiler that says otherwise is a build error; one that cannot say is caught by nandlog_init().
  • A SPI NAND part with a power-of-two number of pages per block.
  • Roughly 15 kB of RAM for a 4 KB-page part, less for a smaller one.
  • No RTOS, heap, or filesystem is required. A mutex is required only if more than one thread calls the library.
