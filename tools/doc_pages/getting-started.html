Getting Started

Install, configure, port, and run.

1. Install

git submodule add https://github.com/hedgetechllc/nandlog.git external/nandlog

There is no build system and nothing to install. Add three source files to your build:

FileNotes
nandlog.cAlways.
chips/nandlog_chip_<PART>.cExactly one, for the part you have fitted.
your nandlog_port.cCopy the template from the repository root and fill in the stubs.

Put the repository root and chips/ on the include path.

Build with -fno-strict-aliasing. This is required, not advisory. The log reads page and metadata headers out of byte buffers by pointer cast, which an optimiser is otherwise entitled to reason around. It costs nothing measurable. -O2 is otherwise fine and worth having.

2. Configure

Edit nandlog_conf.h. Nothing is derived and nothing has a silent default — anything missing is a named compile error.

SettingDefaultMeaning
NANDLOG_HAS_HARDWARE1Set to 0 to compile the library to no-op stand-ins that accept everything and return nothing, so the application above needs no conditionals of its own.
NANDLOG_MAX_PAGE_SIZE_BYTES4096The largest page you are prepared to spend RAM on. Every buffer is sized from this.
NANDLOG_MAX_SPARE_SIZE_BYTES256The same for the spare area.
NANDLOG_BLOCK_ERRORS_BEFORE_REMOVAL3Erase attempts on one block before it is retired. A failed program is never repeated: one program failure retires its block.
NANDLOG_ERASE_AHEAD_BLOCKS2Blocks kept erased ahead of the write head, so a page write never waits on an erase. Each block is erased once, in a call that commits no page — and again at every boot, because an erase a cut interrupted can leave a block that reads erased and programs unreliably, and nothing records a clean shutdown. A device that reboots far more often than it fills a block should set 0.
NANDLOG_PAGE_PLACEMENT_ATTEMPTS3Blocks a single page write may bring into play, its own included, before the log concludes the part will not hold it.
NANDLOG_MAX_EPOCH_DETAILS_BYTES512Largest caller-defined blob stored with each epoch. At most the page size less 320 bytes — 1,728 on a 2 KB page, 3,776 on a 4 KB one — so a slot keeps room for at least 64 runs of passed-over positions: a larger value is a compile error, and nandlog_init() refuses a part whose page it leaves too little room. What it leaves is the list's room, and so how many runs an epoch may pass over before it is sealed: 880 on a 4 KB page at 512, 64 at 3,776. Every figure for that in this guide scales with it. It may change under a log already written: an epoch whose slot then carries longer details than the new value allows, or a longer list than it leaves room for, is sealed whole — slot, pages and list kept — until a new epoch is begun.
NANDLOG_TIMESTAMP_TOLERANCE_MS250How far a timestamp may step backwards before the log treats it as the time base having moved rather than two writers disagreeing. In the units of your timestamps, which the log never interprets.
NANDLOG_BOOT_SALT0A value that differs from one boot to the next, if the host has one — a boot counter kept in RAM that survives a reset, or a random number. The write-head search rotates its first four probes by it, so a device that boots often does not latch the same pages of the log region every time. Any value is safe: it changes which pages a boot reads, never what it finds.
NANDLOG_RECORD_FRAMING1Whether each record carries its own length, so a reader can walk a page without knowing your record types.
NANDLOG_BUSY_POLL_INTERVAL_US10The wait after each poll of the part's BUSY bit.
NANDLOG_BUSY_TIMEOUT_POLLS50000Polls before the part is declared dead. A count, not a time: the port offers no clock, so the wait lasts at least polls × interval — half a second at the defaults — plus the status reads' own time, which is your port's. On an Apollo4 port whose status read takes about 32 µs that is some 2.1 s; allow for it in a watchdog.
NANDLOG_CHIP_PAGE_COPY1Whether a relocated page may be moved inside the chip instead of across the bus.
NANDLOG_PORT_CRC320Whether the port computes the log's CRC-32, in nandlog_port_crc32() — on a hardware engine, say — rather than the library in software. See Porting.
NANDLOG_CRC_TABLE_IN_RAM1Whether the software CRC's lookup table is kept in RAM (1 KiB, as initialized data) rather than as a constant in flash. The table is read once per byte checksummed, so on a part whose flash reads with wait states it is most of the cost.
NANDLOG_CRC_SLICE_BY_40Whether the software CRC takes four bytes a step through four tables rather than one byte through one: about twice the speed on a Cortex-M4, for 3 KiB more table.
NANDLOG_LOG_LEVEL3Which of the library's messages reach nandlog_port_log(): 0 none, 1 those beginning ERROR:, 2 those and the ones beginning WARNING:, 3 every one, the boot's INFO: lines too. Those left out are compiled out, their text with them, and nothing the library does depends on a message: on the Cortex-M4 build, level 0 links about 4.8 KB less flash than level 3.
NANDLOG_PASS_OVER_HEAD_AT_BOOT0Whether a boot that finds the write head part-way into a block passes over the head's page rather than program it. That page is the only one in the log region a residual second program can land on, so with this on there is none there. The price is paid at every such boot, clean or not, since nothing records a clean shutdown: a metadata slot pair written, a position spent, and a run of the epoch's passed-over list taken unless nothing was committed since the boot before — so an epoch is sealed after about 876 such boots on a 4 KB page, 364 on a 2 KB one, and must then be followed by a new one. Off suits a device that reboots far more often than it commits; on, one whose every page matters and whose boots are rare.

Setting the two MAX_ values larger than your part needs costs only unused RAM. A part whose page exceeds the budget is a compile error inside that part's driver.

Choosing NANDLOG_PASS_OVER_HEAD_AT_BOOT

Off, the page at the write head is the one page of the log region a residual second program can land on: a power cut during a commit that left every bit of it erased, so that nothing after the reboot can tell it from an erased page. In the default build's crash-point campaign that happens in about one trial in two hundred, nearly all of them cuts the bitwise model stops before any cell crosses its threshold; a part rated for one program per page then holds a page programmed twice, which may read back now and drift later. On, there is no such page, and the price is paid at every boot whose head is part-way into a block: a slot pair, a position, and a run of the epoch's passed-over list unless nothing was committed since the boot before. The list holds about 876 runs on a 4 KB page (364 on 2 KB), and the epoch is sealed when it fills. So count, for your device, B: the boots an epoch sees with something committed between them.

DeviceSetting
B stays well under the list's room — say under 400 on a 4 KB page, 150 on 2 KB — because it rarely reboots (mains power, a weekly restart) or begins a new epoch every mission, session or download, and power can fail during a programOn: every page that matters is never programmed twice, for a few slot writes a year
Reboots often while it logs — a sensor that wakes and resets every minute and commits now and then, a watchdog-heavy system — so B would reach the list's room within an epoch (876 one-a-minute boots is under fifteen hours)Off: on, the epoch would be sealed and logging stop until the application begins another

3. Port

Copy nandlog_port.c from the repository root into your own tree, delete its #error line, and implement thirteen functions — fourteen if you hand the log's CRC to a hardware engine. Each stub documents what the layer above assumes of it. See Porting for the detail and a complete worked example.

4. Bring the log up

#include "nandlog.h"

if (!nandlog_init())
{
   /* No part fitted, or the port would not open. No other call should be made. */
   return;
}

nandlog_init() opens the port, identifies the part, loads its bad-block table, recovers the current epoch and locates the write head. It is safe to call more than once. nandlog_probe() is the cheaper question for a build that only wants to know whether a part is present.

5. Start an epoch

An epoch is one generation of the log, with its own sequence numbering from zero. Reads cover one epoch at a time. Starting a new one makes everything logged previously unreachable through the API, though it stays on the part until the write head sweeps over it. Anything still buffered for the old epoch is committed to it first.

A part on which no epoch has ever been begun accepts no records. nandlog_store_record() returns NANDLOG_ERR_NO_EPOCH until the first nandlog_begin_epoch(), rather than writing somewhere a reboot would not find.

nandlog_begin_session();
nandlog_begin_epoch(&experiment_details, sizeof(experiment_details));
nandlog_end_session();

A session holds the part powered across a run of operations instead of waking and sleeping it around each one. Epoch operations and reads require one; ordinary logging does not. Sessions do not nest.

The details blob is opaque — the log stores it, checksums it, and hands it back, but never looks inside.

6. Log records

const nandlog_status_t status = nandlog_store_record(RECORD_SAMPLE, milliseconds, &sample, sizeof(sample));
if (status != NANDLOG_OK)
{
   /* Not stored. NANDLOG_ERR_FULL or NANDLOG_ERR_SEALED: begin a new epoch. NANDLOG_ERR_TOO_LARGE: larger
      than a page. NANDLOG_ERR_READING: a read is open and this record needed a page committed. And so on. */
}

record_type and the data are opaque. The timestamp is only ever compared, never interpreted, so its epoch and units are yours. Ignoring the status is allowed; nandlog_get_stats() counts what was refused either way.

This call is cheap but not free every time: a page is committed as soon as the next record will not fit, so it occasionally writes to flash. Records are never split across pages, and one larger than a page is refused rather than corrupting the stream. nandlog_data_bytes_per_page() is how much a page holds on the fitted part.

A partial page only reaches flash when you ask for it:

nandlog_flush(true);                       /* commit whatever is buffered  */
if (nandlog_has_buffered_data()) { ... }   /* anything unwritten in RAM?   */

Call nandlog_flush(true) on a timer and at shutdown. Without it, up to one page of recent records sits in RAM and is lost to an unexpected reboot. A record is durable once the call that committed its page has returned, and not before.

Call nandlog_flush(false) when idle, if you have an idle moment. A call that commits no page is where the log erases the next block ahead of the write head, so no single call has to both program a page and erase a block.

7. Read it back

uint8_t page[NANDLOG_MAX_DATA_BYTES_PER_PAGE];
uint32_t num_pages = 0, num_bytes = 0;

nandlog_begin_session();
nandlog_begin_reading(start_ms, end_ms);     /* 0 for either bound means "no bound" */
nandlog_read_span(&num_pages, &num_bytes);

for (uint32_t i = 0; i < num_pages; ++i)
{
   nandlog_page_header_t header;
   const uint32_t length = nandlog_retrieve_next_page(page, &header);
   if (length == 0)
   {
      /* Unreadable page. This is a gap, not the end of the read:
         header.seq still identifies which page it was. */
   }
}

nandlog_end_reading();
nandlog_end_session();                       /* also ends any open read */

Writing a page is refused while a read is open: a record that would commit one returns NANDLOG_ERR_READING. To keep logging through a long download, open the read only to take its first sequence number and page count, close it, and fetch the pages with nandlog_retrieve_page_by_seq(), which needs no open read (API reference, Logging through a long download). Both time bounds are resolved inside nandlog_begin_reading(), and both err outward — a little extra data for you to filter, rather than dropping data that was asked for.

nandlog_read_span() costs a read of every page in the span when you ask for an exact byte total. That doubles the flash traffic of a download. Pass NULL for num_bytes unless you need the figure exactly — the page count alone is arithmetic and free.

Walking the records in a page

With NANDLOG_RECORD_FRAMING on, a payload can be walked without knowing your record types:

uint32_t offset = 0, record_bytes = 0;
const uint8_t *record = NULL;

while (nandlog_framed_next_record(payload, length, &offset, &record, &record_bytes))
{
   const uint8_t  type = record[0];
   uint32_t timestamp;  memcpy(&timestamp, record + 1, sizeof(timestamp));
   const uint8_t *data = record + 5;
   const uint32_t data_length = record_bytes - 5;
}

8. Check your work

Dump an image from the device and run it through the reference parser, which verifies every CRC independently of the device that wrote it:

./tools/nandlog_parse.py image  dump.bin --page-size 4096 --spare-size 256
./tools/nandlog_parse.py stream offload.bin --json

And run the host test suite, which exercises the real log and chip driver against an emulated part, and the crash-point campaign, which cuts power at every program and erase:

cd sim && make
cd sim && make campaign
cd sim && make exhaustive
