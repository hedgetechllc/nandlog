Complexity

A header read latches a page and clocks out 32 bytes; a raw read latches a page with the part's ECC turned off and clocks out the whole page and spare, which is how a page is shown to be blank.

Turning a position into a page is arithmetic over the sorted list of retired blocks, O(R), with no flash access. A part with more retired blocks than the list holds (NANDLOG_MAX_TRACKED_RETIRED_BLOCKS, 128 by default) still works, asking the driver block by block instead.

Bus traffic versus flash time

Almost everything the log reads is a 32-byte header out of a 4 KB page, so it reads 32 bytes. Boot, the write-head search, the time-bound seek and the sequence-number lookup all use nandlog_chip_read_page_region(). Only nandlog_read_span()'s byte pass needs a whole page, because it verifies payload CRCs.

This saves bus time, not flash time: page-read counts in the table above are unaffected. How much that is worth depends on the platform, and is usually less than the byte counts suggest — see the measurements below.

Over 300 consecutive commits, none also erased: every erase landed in an idle call, one per 64 pages. A warm boot falls as the epoch grows, because more of the search's probes land on written pages, whose headers settle them, and fewer on erased pages, which need a raw read; the first four probes are rotated from boot to boot (see Boot), so a boot's count moves by a few latches either way. A relocation reads each page it moves whole, once, so that the page is judged from a single read — a page a cut tore can read differently from one read to the next — and only a page that reads whole is then copied inside the part. A relocation's programs are the copies, the page itself, the metadata slot recording the failure and the retirement (two pairs), the table's new version (a pair) and the retired block's spare-area mark. The block in that example refuses every program, its mark included, so each boot after tries the mark once more: the one program in the boot after it. A metadata slot is read as a whole page, once, and each bad-block table page the driver reads as its header and entries together, once, which between them are most of the bus bytes a boot reads with ECC on. make opcounts in sim/ regenerates every figure here, splits each call's reads by how much they clock out — at most 64 bytes, less than a page, a page, a page and its spare area — and runs the relocations again without the internal copy, where every page also crosses the bus on its way out: 355 kB read and 197 kB written for the 40-page relocation, 1.06 MB and 563 kB for the worst case, against 193 kB and 33 kB, and 560 kB and 47 kB, with it.

Fitting those two points gives 0.17 µs per byte — 98.2 % of 48 MHz wire speed (690 µs for the 4064 bytes between the two reads, against 677 µs on the wire), so bulk transfer is efficient — and 431 µs of fixed cost per read, independent of length.

That fixed cost is almost entirely the part. Isolating the page latch — the interval during which the part reports itself busy after a read command — by bisection:

The latch is 83 % of a header read, and on-die ECC accounts for 117 µs of it — a fixed cost, identical on an erased page as on a written one, so it is the engine running rather than correction effort. The remaining 104 µs above the datasheet's stated maximum is unexplained; the figure appears to exclude the ECC engine, and this part is a 1.8 V variant while the datasheet quotes one read time for the family. The latch figures come from bisection, so each is a lower bound.

Each nandlog_port_transfer_* call adds about 30 µs of host-side overhead independent of payload, and a status-register read costs the same. The library keeps those calls to a minimum — the status word that ends a busy wait already carries the ECC verdict, so a page read asks the part for its status once rather than three times — but the latch is not something software can shorten.

Budget from measurement, not from the datasheet. The latch alone is 2.6 times the stated 140 µs on this part, and a header read budgeted from that figure plus the host's own overhead — about 215 µs — would be short by a factor of two. tests/ contains the test that produces the table above; run it on your own part before sizing anything around read latency.

A header read is 99 % fixed overhead. Reading 32 bytes instead of 4096 therefore costs 39 % of a whole-page read, not 0.8 %. Over a full epoch of this part — 260,608 pages — a bounded download open takes 114 s rather than 293 s: a real 2.6×, not the 128× the byte counts alone would suggest.

On a platform with lower per-transaction overhead, or a faster bus, the ratio moves toward the byte counts. Measure it on yours before designing around either figure.

Reducing download cost

  • Pass NULL for the byte total unless a host needs it to size a buffer. That removes a whole-page read of every page in the span.
  • Leave the end bound at zero and filter on the host. The end-bound seek is a full pass over the epoch, every time.
  • A start bound alone costs only as far as the page it finds.

Boot

From the simulator counts above and the read costs measured on this part — 436 µs for a header read, 1126 µs for a whole page, and, as an estimate not yet measured, about 1.2 ms for a raw read, which adds two register writes to a whole-page read — plus the measured 973 µs per erase:

EventWorkModelled
Warm boot, one epoch45 short reads, 11 table-page reads of about 1 kB and 3 whole-page reads with ECC on, 16 raw reads, 8 one-byte marker reads with ECC off (counted as header reads), 2 erasesabout 54 ms

First ever boot4103 one-byte marker reads with ECC off and 18 other reads, 1 erase, 3 programsabout 1.8 s, measured 1.79 s for the scan with ECC on

These are models, not measurements: no boot of this build has been timed on hardware. A boot reads the first slot of each ring block, rather than all 512 slots, and binary-searches the newest, and finds the write head in about ⌈log2(N + 1)⌉ = 18 probes: its first four are rotated, boot to boot, over the middle half of what is left to search, by the ring's slot numbering and NANDLOG_BOOT_SALT, which costs at most part of a probe each and spreads what read disturb counts. A table page is modelled as a header read plus its kilobyte at the measured rate, about 606 µs. About a fifth of the latches are raw reads, the price of only ever taking a blank page as evidence — that a probe is past the write head, or that nothing was written after the newest table version or metadata slot. The driver adds one ECC-off read per retired block, to check that its marker is there, so a worn part with a hundred retired blocks pays about a hundred more short reads a boot.

Every boot also erases the blocks ahead of the head again, because an erase a cut interrupted can leave a block that reads erased and programs unreliably, and a boot cannot tell. A device that reboots far more often than it fills a block therefore wears those blocks by up to NANDLOG_ERASE_AHEAD_BLOCKS erases a boot, plus one while the head sits on a block boundary: one boot a minute while logging a page an hour keeps each block in the default two-block window for 128 hours, so it is erased about 7,700 times on each pass of the head — a large share of any part's rated endurance. Setting NANDLOG_ERASE_AHEAD_BLOCKS to 0 leaves a boot only the head's own block to erase, at the price of the commit that enters each block erasing it first.

CRC-32

Every page carries a CRC-32 over its 28-byte header and one over its payload, and every page read is checked against both. Where that work lands:

  • nandlog_store_record() adds its own record to the page's CRC as it copies the record in: the record's length plus 5 bytes, and 2 more with framing.
  • A commit computes only the header's CRC: the payload's is already kept. A page tried again after a failed program, in another block, keeps it too.
  • A page served — nandlog_retrieve_next_page(), by sequence number, from the retransmission list or nandlog_read_recent_page() — costs one payload CRC, the check, and reports the CRC it checked. nandlog_read_span()'s byte total costs one a page as well.
  • Boot and the time-bound seek check one 28-byte header CRC per header read; a relocation, one payload CRC per page it moves through the part, two more for one it moves across the bus.

Each is the library's software unless the port takes the CRC over (NANDLOG_PORT_CRC32, see Porting). Measured and modelled on the Apollo4 Plus at 96 MHz, -Ofast, the buffers in zero-wait TCM:

The CRC of a page's payload is the same work wherever it is done; kept up record by record it is spread over the calls that store, so no call carries it in one piece, and with the table in RAM there is about half as much of it. A port whose engine takes long runs moves the records of 64 bytes or more, and every page served, to the hardware as well.

Blocking time

Measured on an Ambiq Apollo4 Plus (Cortex-M4F) with the Alliance part on a 48 MHz SPI bus, over roughly 488 page writes and 12 erase-ahead activations, using the DWT cycle counter, in the firmware this library was extracted from — the same program-then-read-back commit, without the library's software CRCs and with two erases per activation.

OperationMax observedFrequencyAmortized per page
One page commit2855 – 2893 µsevery page2893 µs
Erase-ahead (2 blocks)1946 – 1989 µsevery 64 pages30 µs

In this library an activation is one erase of about 973 µs, not two, and it runs in a call that commits no page, so the longest a nominal call blocks is one page commit. Only when the window has run dry — no idle call for 128 pages at the default window — does a commit erase the block it is entering itself. A commit computes only its header's CRC, the payload's having been kept up as the records were stored (above), and its read-back clocks out only the header and payload, so a partial page reads back in little more than a header read.

About 16.4 kB of RAM for the Alliance part, 15.4 kB with the CRC's table left in flash. The dominant term is the page budget, so a build that lowers NANDLOG_MAX_PAGE_SIZE_BYTES to match a 2 KB-page part saves about 4 kB. The passed-over list costs no RAM: a boot reads a slot, list and all, into the page buffer, which holds no records until the boot is over.

The only meaningful stack use is in the epoch-listing calls, which build a short array on the stack (128 bytes at the default NANDLOG_MAX_LISTED_EPOCHS of 16) rather than caching a list of epochs in RAM between calls, and a few 64-byte slot heads held while a page is verified. The deepest frame, nandlog_select_epoch(), is 344 bytes at -O2; the deepest chain, by GCC's call graph, is 764 bytes with the Alliance driver and 620 with the Winbond one, from nandlog_init() to the port's transfer (a stub's, of 4 bytes): a boot relocating the head's block to a target that will not erase, whose retirement's slot then meets a ring block that will not erase either, and retires that too. nandlog_store_record()'s deepest is 684 bytes (540 with the Winbond driver), plus the port's CRC where NANDLOG_PORT_CRC32 is set. There is no recursion.

The consistent rule: a page that cannot be trusted is a gap, and a gap is not the end of the log. Reads step over it; offload reports it as a zero-length page carrying its sequence number, so a host can tell "still missing" from "never answered" and ask for it again.
