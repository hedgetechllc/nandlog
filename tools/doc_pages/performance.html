Bus traffic versus flash time

Almost everything the log reads is a 32-byte header out of a 4 KB page, so it reads 32 bytes. Boot, the write-head search, the time-bound seek and the sequence-number lookup all use nandlog_chip_read_page_region(). Only nandlog_read_span()'s byte pass needs a whole page, because it verifies payload CRCs.

This saves bus time, not flash time: page-read counts in the table above are unaffected. How much that is worth depends on the platform, and is usually less than the byte counts suggest — see the measurements below.

Measured: what a read actually costs

Measured on an Ambiq Apollo4 Plus at 48 MHz SPI with on-die ECC enabled, using the DWT cycle counter.

ReadBytesTime
Page header only32436 µs
Whole page40961126 µs

Fitting those two points gives 0.17 µs per byte — 97.7 % of 48 MHz wire speed, so bulk transfer is efficient — and 431 µs of fixed cost per read, independent of length.

That fixed cost is almost entirely the part. Isolating the page latch — the interval during which the part reports itself busy after a read command — by bisection:

ConditionLatch
On-die ECC enabled, written page361 µs
On-die ECC enabled, erased page361 µs
On-die ECC disabled244 µs
Datasheet maximum for a 4 KB page140 µs

The latch is 82 % of a header read, and on-die ECC accounts for 117 µs of it — a fixed cost, identical on an erased page as on a written one, so it is the engine running rather than correction effort. The remaining 104 µs above the datasheet's stated maximum is unexplained; the figure evidently excludes the ECC engine, and this part is a 1.8 V variant while the datasheet quotes one read time for the family.

Each nandlog_port_transfer_* call adds about 30 µs of host-side overhead independent of payload, and a status-register read costs the same. The library keeps those calls to a minimum — the status word that ends a busy wait already carries the ECC verdict, so a page read asks the part for its status once rather than three times — but the latch is not something software can shorten.

Budget from measurement, not from the datasheet. A design that assumed the stated 140 µs would be wrong by a factor of three on this part. tests/ contains the test that produces the table above; run it on your own part before sizing anything around read latency.

A header read is 99 % fixed overhead. Reading 32 bytes instead of 4096 therefore costs 39 % of a whole-page read, not 0.8 %. Over a full epoch of this part — 257,024 pages — a bounded download open takes 112 s rather than 289 s: a real 2.6×, not the 128× the byte counts alone would suggest. A warm boot is 225 ms rather than roughly 690 ms.

On a platform with lower per-transaction overhead, or a faster bus, the ratio moves toward the byte counts. Measure it on yours before designing around either figure.

Reducing download cost

  • Pass NULL for the byte total unless a host needs it to size a buffer. That removes a whole-page read of every page in the span.
  • Leave the end bound at zero and filter on the host. The end-bound seek is a full pass over the epoch, every time.
  • A start bound alone costs only as far as the page it finds.

Relocation

Measured on hardware, per page:

MethodPer pagePer 64-page block
Chip-internal copy1149 µs73 ms
Read into RAM and write back2626 µs168 ms
Saving1477 µs (56 %)95 ms

The saving of 1477 µs is almost exactly the 1390 µs of bus time that 4096 bytes in each direction would have cost, which is what the optimisation was for. Unlike the partial-read case, this one removes whole transfers rather than shortening them — which is why it is worth 56 % and a partial read is worth 39 %.

In simulator bus-traffic terms, retiring one block and relocating the twenty pages already written in it:

What remains in the first row is not the relocation: it is the three full-page program attempts the block refused before it was retired, the bad-block marker page, and the one page that actually had to be written and verified. The relocation itself moves six bytes of address per page.

Boot is dominated by the metadata ring scan, which reads one header from each of 512 slots. Because a header read is almost all fixed cost, that figure is set by the number of reads rather than by their size.

Bounded loops

These loops run in whichever task calls the log, so every one has a stated bound. A part that has stopped accepting programs must not turn a search into a spin that only a watchdog can end.

About 18.4 kB for the Alliance part. The dominant term is the page budget, so a build that lowers NANDLOG_MAX_PAGE_SIZE_BYTES to match a 2 KB-page part saves about 6 kB.

The only meaningful stack use is in the epoch-listing calls, which build a short array on the stack (128 bytes at the default NANDLOG_MAX_LISTED_EPOCHS of 16) rather than caching a list of epochs in RAM between calls.

Failure handling

FailureResponse
Program reports failureRetried; then the block is retired and any pages already written in it are relocated
Written page does not read back with a valid headerSame — the header CRC makes this exact rather than ECC-dependent
Erase reports failureThe block is retired
Power lost mid-programThe torn page fails its CRC on the next boot and is treated as a gap
Power lost mid-eraseThe partially erased block reads as a gap and is rewritten or retired
Payload CRC mismatch on readThat page is reported as zero-length: a gap, not the end of the log
A page will not stay written anywhereRelocation is retried across NANDLOG_PAGE_PLACEMENT_ATTEMPTS blocks, then logging is disabled and nandlog_port_unwritable() is called
Part stops respondingBounded busy-wait, then nandlog_port_fatal()
Bad-block table implausibleIgnored rather than acted on, and rebuilt

The consistent rule: a page that cannot be trusted is a gap, and a gap is not the end of the log. Reads step over it; offload reports it as a zero-length page carrying its sequence number, so a host can tell "still missing" from "never answered" and ask for it again.
